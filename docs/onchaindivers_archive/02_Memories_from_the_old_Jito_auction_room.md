the story is sometimes told. It is 1,000 lamports. The later rate is zero, but the program raises the calculated transfer to that floor.</p><p>These are controlled test values. They are not amounts recovered from a historical auction. Seven illustrative cases and 1,000 generated cases exercised the recovered payment behavior; no live exploit was submitted.</p><h2>What the old auction would have seen</h2><p>The likely sequence reads like a timing diagram:</p><ol><li><p>The operator chooses a cutoff near the expected gap between simulation and execution.</p></li><li><p>The block engine simulates before that cutoff.</p></li><li><p>The early path calculates the large tip.</p></li><li><p>The auction evaluates the bundle using the simulated result.</p></li><li><p>Execution crosses the cutoff.</p></li><li><p>The later path pays the minimum.</p></li></ol><p>The binary and tests support the branch behavior. Jito’s documentation supports the simulation-then-validator pipeline.[1] The missing piece is the auction ledger: we do not have evidence showing that Jito credited the early result, ranked the bundle on that basis, and then accepted the smaller landed payment.</p><p>The program preserves the attempt. It does not preserve the scoreboard.</p><h2>Case file 2: the account that knew whether the world was live</h2><p>The second story comes from the same period, but its evidence is different. This is a recollection from the operator, not a recovered program claim.</p><p>This mechanism required two separate Jito bundles. The first changed a designated account. The second carried the trade and read that account before deciding which path to take:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;62bd8afa-cdb1-4322-9991-7982824c6625&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">bundle A
    change the state of a designated account

bundle B
    read that account
    old state  -&gt; treat this as simulation
    new state  -&gt; treat this as live execution
    then trade accordingly</code></pre></div><p>Why could that work?</p><p>The block engine simulates bundle B against a bank snapshot where bundle A has not landed. The reader sees the old value. On the live path, bundle A lands first and commits the state change. When bundle B executes afterward, its trade sees the new value.</p><p>The account becomes a one-bit witness:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;c3742464-c621-4f5a-87fe-baf3e3b2e34b&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">old value = the earlier write is not visible here
new value = the earlier write has already happened here</code></pre></div><p>Unlike the clock switch, this version does not wait for a slot number to cross a threshold. It asks whether a prior side effect exists in the current view of the world.</p><p>That distinction is useful. Time is only one way to make simulation and execution diverge. Any input that can change between the two observations may become a discriminator: account state, balances, sequence counters, or the presence of a write from an earlier transaction.</p><p>The separation into two Jito bundles is essential. If the state-changing transaction and the trade sat inside one correctly simulated atomic bundle, the simulator should apply the first transaction’s write before running the second. There would be no old-state signal. The trick depends on bundle B being simulated before bundle A’s write is present, then executed after bundle A has landed.</p><h2>Two tricks, one invariant</h2><p>The clock switch and the state latch look different in code, but they pressure the same assumption.</p><p>The auction simulates a bundle because it wants to price what will happen. That works only if the properties used for ranking survive into execution.</p><p>For a tip, the invariant is:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;acc8a271-18c1-47c7-a0e2-758b87991957&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">if simulation values a payment of x,
execution must pay x or fail</code></pre></div><p>For a state-dependent trade, it is broader:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;94d7bfda-964e-455f-9e68-c1a1a8f290fe&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">if simulation ranks a transaction using state s,
execution must not silently choose another economic path under state s'</code></pre></div><p>Atomic execution is not enough. A bundle can be atomic and valid while still making its economically important behavior depend on a clock tick or state change that differs between preview and settlement.</p><h2>What an indexer can recover</h2><p>A chain indexer sees the world after execution. It can record:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;f4b0d4f9-e4af-4d48-8da3-0d73169901ee&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">executed slot

The chain preserved the ending, not the preview Jito used to rank the submission.</p><p>A serious detector needs both views. On-chain data can identify programs with slot branches, suspiciously small landed tips, or trades conditioned on freshly changed accounts. Auction telemetry must show what the simulator observed and what value it assigned to the bundle.</p><h2>What is proven, remembered, and still missing</h2><p>The first case now has a solid artifact trail:</p><ul><li><p>the live sra4 ProgramData account yields the exact ELF from the supplied investigation;</p></li><li><p>the ELF contains both Jito account labels;</p></li><li><p>the disassembly contains a fixed XOR mask, a boundary branch, <code>/10000</code> rate scaling, and a 1,000-lamport floor;</p></li><li><p>isolated tests demonstrate the 0.9 SOL versus 1,000-lamport behavior across the cutoff.</p></li></ul><p>We still do not know which historical auctions, if any, were won this way or how much value was captured.</p><p>The second case is an operator’s recollection. It establishes the intended two-bundle design, but we do not yet have the program, signatures, bundle IDs, or a reproducible test. We are publishing it as oral history while keeping that evidence boundary intact.</p><p>The operator also recalls that Jito later pushed participants toward fixed-size tips. We have not found the original announcement, so that remains attributed. The rationale fits the first failure mode: a fixed payment committed in the submitted transaction cannot shrink merely because the clock advances.</p><p>The old auction room did not leave us a complete diary. It left a live ELF, two wonderfully indiscreet account labels, a hexadecimal mask, and a second story about an account changing state between preview and settlement.</p><p>Sometimes that is enough to reopen the case.</p><div><hr></div><p><em>Research note: On 2026-11-05 UTC, we fetched program </em><code>sra4HHgwsn5Ts6V1TUdLykK1gRJwDQhgscuvXDHxSCx</code><em> through Solana RPC and extracted its ELF from ProgramData account </em><code>BrfLQkZwde23FnZJsHud7MezWhtDxLoe8KUuSXxeibws</code><em>.
