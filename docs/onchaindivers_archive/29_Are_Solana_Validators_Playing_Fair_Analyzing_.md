# Are Solana Validators Playing Fair? Analyzing Block Population Patterns

- **Date**: 2026-04-30
- **Original URL**: [https://onchaindivers.substack.com/p/are-solana-validators-playing-fair](https://onchaindivers.substack.com/p/are-solana-validators-playing-fair)
- **Subtitle**: A question that haunts every Solana trader: Are validators ordering transactions fairly?
- **Description**: A question that haunts every Solana trader: Are validators ordering transactions fairly?

---

<p>In a fair system, transactions should be ordered roughly by when they arrive (FIFO) or randomly. But validators have the power to reorder transactions within their blocks - potentially front-running users, back-running profitable trades, or systematically disadvantaging certain transaction types.</p><p>We analyzed <strong>27,000 recent Solana blocks</strong> (~3 hours of network activity) containing <strong>34+ million transactions</strong> from <strong>600+ unique validators</strong> to answer this question. We tracked not just success/failure status, but also <strong>Jito tip transactions</strong> and <strong>nonce advance transactions</strong> - two key indicators of sophisticated block building and MEV activity.</p><h2><strong>The Topological Map: Visualizing Block Structure</strong></h2><p>Before diving into statistics, let’s see what Solana blocks actually look like. block</p></li><li><p><strong>Transaction statuses</strong>: Success (S), Failure (F), or Vote (V) for each transaction, in order</p></li><li><p><strong>Jito tip positions</strong>: Transactions containing transfers to Jito tip addresses</p></li><li><p><strong>Nonce advance positions</strong>: Transactions with <code>advanceNonce</code> as their first instruction (durable transactions)</p></li></ul><p>We then calculated several metrics for each validator:</p><h3><strong>1. Position Analysis</strong></h3><p>For each transaction type, we computed the <strong>average normalized position</strong> within blocks (0 = front, 0.5 = middle, 1 = back). In a fair system, all types should average around 0.5.</p><h3><strong>2. Clustering Score</strong></h3><p>We measured how much transaction types are <strong>clustered together</strong> vs. randomly distributed. Using a sliding window of 50 transactions, we calculated the variance of type proportions. High variance = clustering.</p><h3><strong>3. Entropy Analysis</strong></h3><p>We computed the <strong>Shannon entropy</strong> of transaction ordering using bigram analysis. Higher entropy = more random/unpredictable ordering. Validators deviating significantly from the mean may face reputation consequences as this type of analysis becomes more common.</p><h2><strong>Technical Details</strong></h2><p>Our analysis used:</p><ul><li><p><strong>Helius RPC</strong> for block data retrieval</p></li><li><p><strong>Position normalization</strong> to compare blocks of different sizes (normalized to 0-1)</p></li><li><p><strong>Running window analysis</strong> (window size: 50 transactions) for clustering detection</p></li><li><p><strong>Bigram entropy</strong> for ordering randomness measurement</p></li><li><p><strong>K-means clustering</strong> (k=5) to identify validator behavior groups</p></li></ul><h3><strong>Data Collection Notes</strong></h3><ul><li><p>Fetched 26,991 consecutive blocks (~3 hours of network activity)</p></li><li><p>Each block averaged 1,259 transactions</p></li><li><p>613 unique validators served as leaders during this period</p></li><li><p>Tracked Jito tip transactions via transfers to known Jito tip addresses</p></li><li><p>Tracked nonce advance transactions via <code>advanceNonce</code> first instruction detection</p></li><li><p>All raw data stored in compressed JSON format for reproducibility</p></li></ul><h2><strong>Conclusion</strong></h2><p><strong>The good news</strong>: Most Solana validators appear to order transactions fairly. The mean success position (0.586) is only slightly back-loaded, and entropy scores generally indicate reasonable randomness.</p><p><strong>The nuanced news</strong>: Clear behavioral clusters exist. Some validators (Cluster 1) use a buffer-and-sort strategy, letting votes pass while accumulating user transactions for priority sorting. Others show notably low entropy. 9 validators show statistically significant success front-loading.</p><p><strong>The open question</strong>: Is the variation we observe due to:</p><ol><li><p>Technical differences in validator client implementations?</p></li><li><p>Network latency and transaction arrival patterns?</p></li><li><p>Intentional ordering for MEV extraction?</p></li></ol><p>Further analysis with larger datasets and correlation to profits would help distinguish these possibilities.</p><p>As Solana’s validator set evolves and MEV infrastructure matures, monitoring validator ordering behavior will become increasingly important for maintaining network health and user trust.</p><div><hr></div><p><em>Data and analysis scripts available in our research repository.
