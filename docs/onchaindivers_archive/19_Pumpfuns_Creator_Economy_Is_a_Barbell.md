Two addresses can produce the same number of tokens while operating completely different launch systems.</p><h2><strong>What migration measures, and what it misses</strong></h2><p>A migration is an observable protocol milestone: the mint appears in <code>pfamm_migrations</code> after being created in <code>pumpfun_token_creation</code>.</p><p>It is not the same as lasting success.</p><p>Migration alone does not tell us:</p><ul><li><p>whether liquidity persisted;</p></li><li><p>whether trading remained broad after migration;</p></li><li><p>whether volume came from independent participants;</p></li><li><p>whether the token retained value;</p></li><li><p>whether the creator controlled multiple apparently independent wallets.</p></li></ul><p>The cohort is also right-censored. Wallet and funding clusters would also help distinguish independent creators from address rotation.</p><h2><strong>Reproduce the creator statistics</strong></h2><p>The migration table in the indexer is named <code>default.pfamm_migrations</code>. Both <code>mint</code> and <code>creator</code> from the creation table are normalized because the <code>FixedString</code> values can contain trailing NUL bytes.</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;sql&quot;,&quot;nodeId&quot;:&quot;58b5e3d6-d87d-4950-972a-3cf8b66bd749&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-sql">WITH
    toDateTime('2026-07-06 00:00:00', 'UTC') AS start_time,
    toDateTime('2026-08-06 00:00:00', 'UTC') AS end_time,

    created AS
    (
        SELECT
            replaceAll(toString(mint), char(0), '') AS mint,
            argMin(
                replaceAll(toString(creator), char(0), ''),
                tuple(block_time, slot, tx_idx)
            ) AS creator,
            min(block_time) AS created_at
        FROM default.pumpfun_token_creation
        WHERE block_time &gt;= start_time
          AND block_time &lt; end_time
        GROUP BY mint
    ),

    migrated AS
    (
        SELECT
            replaceAll(toString(mint), char(0), '') AS mint,
            min(block_time) AS migrated_at
        FROM default.pfamm_migrations
        PREWHERE block_date_utc &gt;= toDate(start_time)
             AND block_date_utc &lt;= toDate(end_time)
        WHERE block_time &gt;= start_time
          AND block_time &lt; end_time
        GROUP BY mint
    )

SELECT
    c.creator,
    count() AS tokens_created,
    countIf(length(m.mint) &gt; 0) AS tokens_migrated,
    round(
        100.0 * tokens_migrated / tokens_created,
        2
    ) AS migration_rate_pct,
    toTimeZone(min(c.created_at), 'UTC') AS first_creation_utc,
    toTimeZone(max(c.created_at), 'UTC') AS last_creation_utc
FROM created AS c
LEFT JOIN migrated AS m USING (mint)
WHERE length(c.creator) &gt; 0
GROUP BY c.creator
ORDER BY
    tokens_created DESC,
    tokens_migrated DESC,
    c.creator
FORMAT CSVWithNames</code></pre></div><p>The explicit <code>toTimeZone(..., 'UTC')</code> conversion matters because the ClickHouse server’s default timezone can otherwise change how <code>DateTime</code> output is displayed, even when the filter boundaries are defined in UTC.</p><h2><strong>Reproduce the scatter plot</strong></h2><p>Assuming the SQL output is saved as <code>creator_stats.csv</code>:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;python&quot;,&quot;nodeId&quot;:&quot;c135075a-07df-4e3a-b4d7-5db7715209e2&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-python">import numpy as np

    cmap="viridis",
