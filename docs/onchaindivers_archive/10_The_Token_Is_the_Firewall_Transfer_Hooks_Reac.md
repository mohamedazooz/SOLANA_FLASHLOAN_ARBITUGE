Meteora documented transfer-hook pools in its v0.2.0 release and describes them as Token-2022 pools whose hook is revoked when the curve completes, before migration to DAMM v2.[1][2][6]</p><p>What was new to the indexer was the <strong>creation path</strong>—and what followed was more interesting than a decoder update. In a 46-minute fixed window, <strong>ten …hook mints</strong> appeared and generated <strong>1,132 landed transactions</strong>. Several were not merely themed around “hooks.” Their hooks actively rejected transactions based on wallet holdings, slot-level buy activity and required signers.</p><h3>What happened in the triggering transaction</h3><p>The triggering transaction did four things atomically:[4]</p><ol><li><p>Created the Token-2022 mint Epbi37…Jhook and initialized its metadata as <strong>HOOKED CAT / HOOKCAT</strong>.</p></li><li><p>Set the mint’s Transfer Hook extension to the executable program GE5TW1…P5sLV.</p></li><li><p>Called Meteora DBC’s initialize_virtual_pool_with_token2022_transfer_hook instruction and created the bonding-curve pool 7M1Nho…rpvT.</p></li><li><p>Bought 353,973.181518 HOOKCAT for 0.01 SOL in the same transaction through swap2_with_transfer_hook.</p></li></ol><p>The token output moved through Token-2022’s TransferChecked instruction. Token-2022 then invoked the configured hook program. The hook accepted the transfer, so the buy settled. The full transaction consumed 214,850 compute units and paid a 25,218-lamport transaction fee.</p><p>This distinction matters: <strong>the hook is not the exchange and does not calculate the DBC price.</strong> Meteora’s curve performs the swap. The hook is an additional program called during the resulting token movement.</p><h3>What a transfer hook actually is</h3><p>A Token-2022 mint can store the address of a Transfer Hook program. Whenever that mint is transferred, Token-2022 performs a cross-program invocation, or CPI, into the hook’s Execute instruction. The hook can inspect the transfer and extra accounts, update its own state, perform permitted CPIs, or return an error and roll back the entire transaction.[3]</p><p>The flow is:</p><p>DBC buy or sell</p><p>→ Token-2022 TransferChecked</p><p>→ configured hook program</p><p>→ <strong>PASS:</strong> transfer and swap settle</p><p>→ <strong>ERROR:</strong> the whole transaction reverts</p><p>Extra state is discovered through a standardized extra-account-metas PDA. This is why hook-aware clients need more than the source token account, mint, destination and owner: they must resolve and append the accounts expected by the hook.[3]</p><p>Token-2022 deliberately de-escalates the original transfer accounts to read-only inside the hook and does not pass through the sender’s signer privilege. That reduces one class of malicious-hook behavior, but it does not make the token permissionless. <strong>The hook can still decide whether a transfer is valid.</strong>[3]</p><h3>What the hooks were doing in the new tokens</h3><p>The current GE5TW1…P5sLV binary exposes a launch-guard system rather than one fixed policy. Its embedded program messages include paths for allowlists and blocklists, launch-window wallet caps, trading hours, venue restrictions, anti-bundle limits, required co-signers, per-trade supply caps, sniper-fee checks and fee/burn logic.[5]</p><p>Those are capabilities of the program—not proof that every token enables every rule. To separate capability from use, we examined a partial RPC sample of 522 recent transactions involving the program and matched guard failures to their Token-2022 mints.</p><p>Four behaviors were Measuring guard pressure therefore requires both datasets: landed swaps from the indexer and failed transaction logs from RPC.</p><h3>The real change: launch rules move on-chain</h3><p>Most launch controls live outside the token: frontend limits, API throttles, allowlisted relays or social promises. Transfer hooks move policy into the settlement path. <strong>If the hook rejects a transfer, changing the frontend does not help.</strong></p><p>That creates three practical consequences.</p><h4>1. “Tradable” becomes route-dependent</h4><p>A wallet or router that knows ordinary SPL transfers may still fail on a hook-enabled Token-2022 mint. It must load the mint extension, resolve the extra-account metadata, append the required PDAs and satisfy the hook’s transaction-context rules. A quote can be economically correct and still be operationally unexecutable.</p><h4>2. Wallet distribution can be enforced, not merely observed</h4><p>A one-percent wallet cap is no longer a dashboard metric or launch guideline. It is a state transition constraint. Likewise, an anti-bundle rule can reject the third buy in a slot even if the buyer uses a different transaction.</p><p>This does not eliminate concentration. Multiple wallets, transfers after the launch window, exemptions, or rule changes can still alter outcomes. But it changes the adversarial surface from “ignore the UI” to “satisfy on-chain code.”</p><h4>3. The rules are temporary—and upgradeable</h4><p>Meteora’s documented model revokes the transfer hook at curve completion so the token can migrate to DAMM v2 without ongoing hook restrictions.[1] A token therefore has two regimes:</p><p><strong>bonding curve:</strong> programmable transfer policy</p><p><strong>post-migration:</strong> hook revoked, ordinary downstream liquidity behavior</p><p>There is also a trust boundary before revocation. The observed hook program is upgradeable, and its current ProgramData records upgrade authority a1PFRx…8Z23.[5] The active binary can therefore change while launch tokens still point to it. Users should treat the hook program, its configuration and its upgrade authority as part of the token’s risk surface.</p><h3>What indexers should store</h3><p>Parsing the creation discriminator is only the first step. A useful launch record should preserve:</p><ul><li><p>hook program ID and hook authority;</p></li><li><p>extra-account-metas PDA and hook configuration PDA;</p></li><li><p>decoded guard parameters, including basis-point caps and slot limits;</p></li><li><p>whether a transaction failed in the hook and the guard error logged;</p></li><li><p>the exact point when the hook is revoked;</p></li><li><p>pre- and post-revocation trading regimes.</p></li></ul><p>The current landed swap table already captures swap2_with_transfer_hook activity, but the triggering creation was absent from the creation table because the creation discriminator was unknown. That gap is analytically important: without the creation row, the first swap appears without the launch configuration that governs it.</p><p>The signal was not simply “Meteora added another instruction.” It was that token transfer policy became a first-class launch variable. For ML-native traders, the next feature set is not only price, flow and creator history.
