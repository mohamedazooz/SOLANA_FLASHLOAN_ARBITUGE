protocol. Its first phase, <strong>Votor</strong>, handles voting and finalization. <strong>Rotor</strong>, the planned replacement for Turbine’s block-distribution system, is not part of this first deployment.[1][6]</p><p>Votor runs two finalization routes concurrently:</p><ul><li><p>an 80%-stake fast path that can finalize after one voting round;</p></li><li><p>a two-round path using 60%-stake thresholds.</p></li></ul><p>Whichever route completes first wins. The target is approximately <strong>150ms finality</strong>, rather than TowerBFT’s roughly 12.8-second process. This is finality latency, not block time.[1][10]</p><p>Transaction execution did not move off-chain. The SVM, transaction format, programs, state changes, failed transactions, and fee mechanics continue to operate normally.</p><h3>The exact activation boundary</h3><p>There were two distinct moments:</p><p><strong>Feature activation</strong><br>slot 459,648,000<br>2026-10-21 13:36:05 UTC</p><p><strong>Last TowerBFT / Alpenglow genesis block</strong><br>slot 459,652,999<br>2026-10-21 13:54:00 UTC</p><p><strong>Votor begins</strong><br>slot 459,653,000</p><p><strong>First produced Votor block</strong><br>slot 459,653,008<br>2026-10-21 13:54:03 UTC</p><p>Slots 459,653,000–459,653,007 were skipped. The first produced Votor block points directly to the certified TowerBFT genesis block.</p><p>Our primary census uses equal 24-hour UTC windows around the first indexed Votor block, rather than equal slot ranges. This avoids bias from changes in slot duration and produced-block count.</p><h3>Transaction count: a structural break, not a user exodus</h3><p>The indexer recorded <strong>441.6 million</strong> Median leader reward moved from <strong>0.00851 SOL</strong> to <strong>0.00676 SOL</strong> per block; total 24-hour leader rewards moved from <strong>6,453.55 SOL</strong> to <strong>5,600.17 SOL</strong>.</p><p>Priority-fee movement cannot be assigned to Votor from this event window. Priority fees respond to user demand, account contention, requested CU limits, bidding behavior, and scheduler conditions. Votor did not change the fee formula.[1][2]</p><p>Validators no longer pay one transaction fee for every consensus vote. Instead, admitted validators pay the current <strong>0.8 SOL Validator Admission Ticket per epoch</strong> from their vote account.[3] Older draft material mentioning 1.6 SOL per epoch is not the live value.</p><h3>What can be concluded?</h3><p>The clean effects are structural:</p><ol><li><p>Routine vote transactions fell to zero after the boundary.</p></li><li><p>Recorded transaction count fell sharply because those votes disappeared.</p></li><li><p>Vote signature fees and vote CU consumption disappeared from blocks.</p></li><li><p>Leader fee revenue fell over this particular comparison window.</p></li><li><p>Non-vote load and priority fees remained demand-driven; their changes are not causally identified by a before/after chart.</p></li><li><p>Validator voting continues through direct messages and aggregate certificates.</p></li></ol><div><hr></div><h3>Appendix A: How the migration was made safe</h3><h4>A controlled handoff</h4><p>SIMD-0384 specified a migration boundary 5,000 slots after feature activation. During the transition, validators restricted TowerBFT blocks so ordinary user transactions could not enter the rollback region. They then waited for a strongly confirmed final TowerBFT ancestor and voted on it as the Alpenglow genesis block.[7]</p><p>Because transitional blocks carried no new user transactions, incompatible descendants could be discarded without rolling back newly accepted user activity.</p><h4>The 82% genesis certificate</h4><p>Validators switched only after receiving a BLS genesis certificate representing <strong>at least 82% of stake</strong>. The migration argument assumes at most 19% malicious stake: two contradictory certificates above 82% could not both be formed without honest validators signing conflicting genesis blocks.[7]</p><p>The certificate was rebroadcast and embedded in initial Alpenglow metadata. A validator starting from a snapshot could verify the migration-success state, while a lagging validator could recover after observing a valid finalization certificate.</p><h4>Prerequisites and rehearsals</h4><p>Before the switch:</p><ul><li><p>BLS public-key registration activated on mainnet;</p></li><li><p>registrations required proof of possession bound to the vote account, protecting aggregate signatures from rogue-key attacks;</p></li><li><p>validators without an eligible BLS key were excluded from consensus;</p></li><li><p>the migration was rehearsed on a community cluster, testnet, and devnet;</p></li><li><p>the initial migration required a compatible Agave-based client.[1][3][8]</p></li></ul><h4>Security model</h4><p>Alpenglow uses a “20+20” model. Its core safety assumption is <strong>strictly less than 20% Byzantine stake</strong>; the additional offline tolerance applies under the protocol’s stronger network conditions. This differs from conventional one-third-BFT assumptions.[6][10]</p><p>The white paper supplies safety and liveness arguments, but we found no separately published machine-checked proof or named external audit report.</p><h3>Appendix B: Can the votes still be explored?</h3><h4>Historical votes</h4><p>Yes. Before slot 459,653,000, routine votes remain ordinary historical transactions involving:</p><div class="highlighted_code_block" data-attrs="{&quot;language&quot;:&quot;plaintext&quot;,&quot;nodeId&quot;:&quot;27006ec6-83bc-4204-a9a1-c5e4c003585b&quot;}" data-component-name="HighlightedCodeBlockToDOM"><pre class="shiki"><code class="language-plaintext">Vote111111111111111111111111111111111111111</code></pre></div><p>They can be inspected using an archival getBlock, Solana Explorer, Solscan, or a transaction indexer.[5]</p><h4>Post-Votor individual votes</h4><p>Not through ordinary transaction history. Individual votes now:</p><ul><li><p>travel directly between validators;</p></li><li><p>live in validator consensus data structures;</p></li><li><p>do not receive transaction signatures;</p></li><li><p>do not appear in getTransaction or explorer transaction counts.</p></li></ul><p>Vote accounts still exist on-chain. Administrative changes, withdrawals, commission changes, and BLS-key registration can still produce Vote Program transactions. These are not routine per-slot consensus votes.</p><h4>Certificates and footers</h4><p>Agave’s Geyser interface provides an opt-in block-footer callback. A footer may expose a finalization certificate and reward-related certificates, together with the bank hash and producer metadata.[1]</p><p>Certificate fields are optional, and a footer normally carries the latest certificate the leader knew while constructing the block—not a certificate finalizing the same block. Standard JSON-RPC does not expose every Votor vote, and a full certificate feed currently requires validator or Geyser-level instrumentation.</p><p>The activation itself can be checked using the Alpenglow feature account, while compatible nodes expose the certified migration genesis through getAgGenesisCert.</p><h3>Methodology and limitations</h3><ul><li><p>Indexer census: every produced block in equal 24-hour UTC windows around the first indexed Votor block.</p></li><li><p>Event chart: hourly aggregates from the same Solana block indexer.</p></li><li><p>RPC decomposition: 25 evenly spaced blocks on each side, approximately one every 30 minutes.</p></li><li><p>Vote classification: presence of the native Vote Program in static transaction account keys.</p></li><li><p>Priority-fee estimate: meta.fee − 5,000 × required signatures, floored at zero.</p></li><li><p>CU metric: actual meta.computeUnitsConsumed; requested limits were not measured.</p></li><li><p>“Non-vote” includes user transactions and non-vote system transactions.</p></li><li><p>This is an event study, not a causal experiment.</p></li></ul><h3>Sources</h3><p>[1] Alpenglow | Solana — <a href="https://solana.com/upgrades/alpenglow">https://solana.com/upgrades/alpenglow</a></p><p>[2] Fees | Solana — <a href="https://solana.com/docs/core/fees">https://solana.com/docs/core/fees</a></p><p>[3] BLS Pubkey and the Validator Admission Ticket | Solana — <a href="https://solana.com/upgrades/bls-pubkey-vat">https://solana.com/upgrades/bls-pubkey-vat</a></p><p>[5] getBlock RPC | Solana — <a href="https://solana.com/docs/rpc/http/getblock">https://solana.com/docs/rpc/http/getblock</a></p><p>[6] SIMD-0326: Alpenglow — <a href="https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0326-alpenglow.md">https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0326-alpenglow.md</a></p><p>[7] SIMD-0384: Alpenglow migration — <a href="https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0384-alpenglow-migration.md">https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0384-alpenglow-migration.md</a></p><p>[8] SIMD-0387: BLS pubkey management — <a href="https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0387-bls-pubkey-management-in-vote-account.md">https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0387-bls-pubkey-management-in-vote-account.md</a></p><p>[10] Solana Alpenglow Consensus White Paper v1.1 — <a href="https://www.anza.xyz/alpenglow-1-1">https://www.anza.xyz/alpenglow-1-1</a></p><div><hr></div><p><em>OnChain Divers provides decoded Solana data: launch, swap and migration data for researchers building lifecycle-aware market models.
